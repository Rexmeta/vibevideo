좋아. 지금 VibeVideo의 상태라면 **다음 작업은 Provider 연동보다 먼저 “생성 작업을 상용 SaaS 수준으로 안전하게 만드는 것”**에 집중하는 게 맞아.

현재까지의 변경을 기준으로 우선순위를 다시 잡으면 다음 순서가 가장 좋다.

## 1. P0 — Generation Intent + Idempotency

**다음 작업 1순위**

현재는 `Generation Contract`와 `JobOrchestrator`가 생겼지만,

> 같은 요청이 재시도되었을 때 동일 생성 작업인지 구분하는 장치

가 아직 부족하다.

### 목표

```text
User Action
   ↓
GenerationIntent
   ↓
idempotencyKey
   ↓
GenerationJob
   ↓
Provider Operation
   ↓
Asset
```

예:

```ts
GenerationIntent {
  intentId
  projectId
  sceneId
  capability: "image" | "video" | "audio"
  inputHash
  model
  provider
  idempotencyKey
  createdAt
}
```

같은 `idempotencyKey`로 다시 요청하면:

```text
첫 요청 → 실제 생성
두 번째 요청 → 기존 Job 반환
```

이렇게 되어야 한다.

### 핵심

`commandId`와 `idempotencyKey`를 분리해야 한다.

```text
commandId
= 이번 실행을 식별

idempotencyKey
= 같은 생성 요청인지 식별
```

이 작업이 **가장 먼저**다.

---

# 2. P0 — GenerationJob을 독립 Domain으로 분리

현재 `GenerationRun`이 프로젝트에 상당히 많이 붙어 있다.

앞으로는 구조를 이렇게 가져가는 게 좋다.

```text
Project
 └─ Scene

GenerationRun
 └─ 여러 GenerationJob

GenerationJob
 ├─ image generation
 ├─ video generation
 ├─ audio generation
 └─ ...

Asset
 └─ 실제 생성 결과
```

예:

```ts
GenerationJob {
  jobId
  projectId
  sceneId
  intentId

  capability
  provider
  model

  status
  progress

  idempotencyKey

  providerOperationId

  outputAssetId

  attempts
  createdAt
  startedAt
  completedAt
  failedAt
}
```

### 상태도 명확히

```text
queued
  ↓
running
  ↓
provider_pending
  ↓
uploading
  ↓
completed

        ↘ failed
        ↘ cancelled
        ↘ interrupted
```

이렇게 되면 현재 `JobManager`와 `GenerationRun`의 책임이 훨씬 명확해진다.

---

# 3. P0 — Asset State를 분리

현재 VibeVideo에서는 생성 결과와 Scene/Project 상태가 상당히 얽혀 있다.

상용화하려면 다음을 분리하는 게 좋다.

```text
Asset
```

예:

```ts
Asset {
  assetId
  projectId
  sceneId

  type: "image" | "video" | "audio"

  status:
    "generating"
    | "uploading"
    | "ready"
    | "failed"

  storageKey
  mimeType
  duration
  width
  height

  provider
  model

  createdAt
}
```

그러면:

```text
GenerationJob
      ↓
Asset
      ↓
Scene
```

구조가 된다.

이게 나중에 **Asset Library / Timeline / Versioning / Remix**의 기반이 된다.

---

# 4. P0 — Project Revision / Atomic Save

이건 현재 구조에서 꽤 중요하다.

현재 여러 곳에서 프로젝트를 저장할 수 있기 때문에:

```text
Full Project Save
Scene Map Patch
Generation Run Patch
Operation Patch
Upload Completion Patch
```

서로 덮어쓸 가능성이 있다.

따라서:

```ts
ProjectSnapshot {
  revision: number
}
```

또는

```text
revision = 17

save(revision=17)
     ↓
server revision=18
```

식의 optimistic concurrency control을 넣는 게 좋다.

### 목표

```text
A tab → revision 17
B tab → revision 17

A save → revision 18

B save(revision 17)
       ↓
CONFLICT
```

이렇게 해야 한다.

**상용 서비스에서 데이터 유실 방지를 위해 매우 중요하다.**

---

# 5. P1 — Provider Adapter

여기서부터 Provider 추상화를 제대로 만든다.

현재:

```text
generationCommands
       ↓
geminiService
       ↓
Google
```

이 구조다.

목표:

```text
generationCommands
       ↓
GenerationProvider
       ↓
Provider Router
       ↓
 ┌──────────┬──────────┬──────────┐
 │ Google   │ Runway   │ Kling    │
 │ Veo      │          │          │
 └──────────┴──────────┴──────────┘
```

예:

```ts
interface VideoGenerationProvider {
  generate(input): Promise<ProviderGenerationResult>
  getStatus(operationId)
  cancel?(operationId)
}
```

Google은:

```ts
GoogleVideoProvider
```

가 담당.

이때 기존 `geminiService.ts`를 한 번에 없애면 안 된다.

**Adapter로 감싸는 방식**이 안전하다.

# 6. P1 — Provider Registry + Model Router

Provider Adapter 다음이다.

```text
Provider Registry

google
runway
kling
luma
...
```

그리고:

```text
Model Router
```

가

```text
quality
speed
cost
duration
resolution
capability
```

등을 기준으로 선택하게 한다.

최종적으로는:

```text
Generate Video
      ↓
Production Intent
      ↓
Model Router
      ↓
"Veo"
      ↓
Google Adapter
```

가 된다.

이것이 나중에 **AI Director**의 핵심 기반이다.

# 7. P1 — Browser → Server Generation Gateway

이 단계부터 상용화의 성격이 크게 바뀐다.

현재 가장 큰 구조적 문제 중 하나가:

```text
Browser
  ↓
Google API
  ↓
Veo
```

라는 점이다.

상용 SaaS에서는:

```text
Browser
  ↓
VibeVideo API
  ↓
Generation Gateway
  ↓
Provider
```

로 가야 한다.

특히 API Key를 브라우저에 두는 구조는 최종적으로 제거해야 한다.

# 8. P1 — Worker / Durable Job

그 다음:

```text

 ↓

 ↓
```

구조를 만든다.

# 9. P2 — Scene Graph

여기서부터 VibeVideo의 차별화 영역이다.

현재 Scene은 이미 상당히 많은 production 정보를 가지고 있다.

이걸 발전시켜:

```text
Project
   ↓
Production Plan
   ↓
Scene Graph
   ↓
Scene
   ↓
Shot
   ↓
Asset
```

구조를 만든다.

예:

```text
Scene 01
 ├─ Character: A
 ├─ Location: Office
 ├─ Emotion: nervous
 ├─ Shot: medium
 ├─ Camera: dolly-in
 └─ Asset versions
```

# 10. P2 — Character Bible

이건 상당히 중요하다.

AI 영상에서 가장 큰 문제 중 하나가:

> Scene마다 캐릭터가 달라지는 것

이기 때문이다.

따라서:

```text
Character
 ├─ identity
 ├─ appearance
 ├─ wardrobe
 ├─ personality
 ├─ reference images
 └─ consistency rules
```

를 별도 Domain으로 만든다.

그리고 Scene이 이를 참조한다.

```text
Character Bible
       ↓
Production Plan
       ↓
Scene
       ↓
Image Generation
       ↓
Video Generation
```

# 11. P2 — AI Critic → AI Director

현재 이미 `Vision Critic`이 있으므로 이걸 발전시키는 게 좋다.

### AI Critic

```text
생성
 ↓
평가
 ↓
문제 발견
 ↓
수정 제안
```

### AI Director

```text
Production Brief
      ↓
Scene Graph
      ↓
현재 상태 분석
      ↓
모델 선택
      ↓
Prompt 생성
      ↓
Generation
      ↓
Critic
      ↓

      ↓
```

즉,

**AI가 단순히 영상을 생성하는 것이 아니라 제작 과정을 관리하게 만드는 것**이다.

## 특히 중요한 점

**지금 당장 `Runway`, `Kling`, `Luma`부터 붙이지 않는 게 좋다.**

현재 VibeVideo의 병목은 모델 숫자가 아니다.

```text
생성 요청
   ↓
중복 방지
   ↓
Job
   ↓
Provider
   ↓
Asset
   ↓
Project
```

이 lifecycle이 확실해야 한다.

이걸 먼저 만들면 이후 Provider가 3개든 10개든 추가하기 쉬워진다.

반대로 지금 Provider부터 늘리면:

```text
geminiService
jobManager
uploadQueue
storageService
WizardContext
```

곳곳에 Provider 분기문이 퍼지면서 다시 강한 coupling이 생길 가능성이 높다.

### 따라서 다음 Vibe Coding 작업은 딱 하나로 잡는 것을 권한다.

> **“Generation Intent + Idempotency + GenerationJob을 도입하되, 기존 Generation Contract / JobOrchestrator / ProjectSnapshot을 깨뜨리지 않는다.”**

이것을 첫 번째 티켓으로 만들고 **테스트까지 통과시킨 뒤** 다음 티켓으로 넘어가는 방식이 가장 안전하다.
